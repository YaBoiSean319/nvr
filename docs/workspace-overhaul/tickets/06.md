# [Workspace 06] Extend synchronized playback to sixteen real camera feeds

Canonical issue: https://github.com/YaBoiSean319/nvr/issues/55

## Parent

https://github.com/YaBoiSean319/nvr/issues/49

## What to build

Raise the complete Playback path from its existing eight-camera bound to sixteen while preserving bounded resource use and readable capacity handling.

Design reference and implementation handoff: https://github.com/YaBoiSean319/nvr/tree/docs/workspace-overhaul-2026-10-22/docs/workspace-overhaul

## Acceptance criteria

- [ ] Timeline/query validation, selected-camera state, coverage/media retrieval, shared-clock playback and all related API admission paths accept 1–16 deduplicated cameras and reject overflow coherently.
- [ ] Do not merely expose larger layouts: generated playable footage proves actual 16-camera retrieval/decoding and synchronization, including empty, slow and failing cameras.
- [ ] Bound metadata fan-out/windowing or pagination, concurrent requests, decoders and media leases; a single slow/unavailable camera cannot freeze the workspace.
- [ ] Preserve the existing 24-hour range and unrelated resource protections unless a documented measured requirement justifies a separate change.
- [ ] Adding/removing at the 8/9/16 boundaries keeps clock, pause/play state, marks and unaffected viewers; reject stale responses after selection changes.
- [ ] Measure reference-environment seek behavior under the declared workload and preserve API authorization/source lease cleanup on all termination paths.
